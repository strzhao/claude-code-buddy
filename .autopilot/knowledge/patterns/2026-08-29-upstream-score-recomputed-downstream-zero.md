# 上游算好分数返回时丢弃、下游用另一字段重打分 → 0 分行进排序列表

<!-- tags: scoring, alias, appindex, unified-score, re-scoring, search, sort, score-drop, candidate -->

**Scenario**: 搜索索引层检索时用**多别名**（显示名 + bundle 标识符成分等）打分选 Top-N，返回时只带实体不带分数；下游构造候选行时用**显示名**重新打分填 score。多源候选合并统一排序时暴露：alias 命中而显示名不命中的行 score=0，仍进列表（挤占截断名额、排尾部），且「输别名第一名应为目标实体」的产品锚点在真实链路失效——mock 固定分数的单测发现不了。

**Lesson**:
- **分数属于检索结果的一部分，谁算谁携带到底**：索引/检索层算出的分必须随结果传递给最终排序消费点；禁止「上游算、下游对另一个字段重算」的双轨——两个打分口径（别名集 vs 显示名）天然不一致，不一致就是 0 分或错分。
- 多源统一排序的验收**必须含真实打分链路锚点**（真实索引 + 真实别名查询断言第一名与分数非 0），mock 固定分数的排序断言只验证排序机制、验证不了分数来源。
- 0 分行混入统一列表同时违反「0 分不进列表」量纲契约——统一量纲体系落地时，既有源的「隐性 0 分」路径要在 QA 反查（反向枚举分数来源风险面）里显式过一遍。

**Evidence**: 统一混排 QA（2026-08-29）：`debug candidates sn` 真实输出尾部出现 app 行 score=0；`debug candidates wechat` 修复前微信（显示名中文、alias 英文命中）score=0 不进列表，修复后 alias 分数携带（完全匹配 1000+位置加成 50）唯一第一。qa-reviewer 独立审查抓出（红队场景 2 mock 固定 1000 分绕过真实链路未捕获）。修复 = 检索层新增带分数返回（scoredSearch），下游直接用携带分。（核对锚点：2026-08-29 源码版本）
